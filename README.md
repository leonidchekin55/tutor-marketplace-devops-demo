# КодСтарт — демо-маркетплейс репетиторов

Статическая адаптивная страница на русском языке для вымышленного маркетплейса занятий программированием для детей. Проект демонстрирует короткий CI/CD-процесс без собственного сервера и секретов хостинга.

## Как устроен CI/CD

GitHub Actions запускает workflow при каждом pull request в `main`, push в `main` и вручную. Сначала runner получает код, устанавливает pnpm и Node.js 22, затем зависимости из зафиксированного lock-файла, ESLint и модульные тесты. Только при успешном завершении проверок для push в `main` (или ручного запуска) загружается артефакт и отдельная job публикует его в GitHub Pages. Pull request проверяется, но не публикуется. Права Pages выдаются только задаче деплоя; параллельные запуски для одной ветки отменяются, чтобы не публиковать устаревший результат.

GitHub Pages выбран для простой статической демо-страницы: отдельный сервер, контейнеры и секретный токен хостинга не нужны. В настройках репозитория включён источник **GitHub Actions**. Публичный URL: https://leonidchekin55.github.io/tutor-marketplace-devops-demo/ После публикации workflow повторно проверяет сайт по выданному Pages URL: ожидает успешный HTTP-ответ и сверяет заголовок страницы. Короткие задержки распространения деплоя переживаются повторными запросами.

## Мониторинг доступности и ошибок

### Внешняя проверка сайта

Создать в UptimeRobot HTTP(s)-монитор с именем `КодСтарт — production` и адресом https://leonidchekin55.github.io/tutor-marketplace-devops-demo/. Для бесплатного плана настроить интервал 5 минут. Проверять код ответа 200; дополнительно создать keyword-монитор на строку `КодСтарт — программирование с интересом`, чтобы заметить случайную публикацию не той страницы. Назначить основным контактом email владельца, а вторым — Slack или резервный email. Включить уведомления при недоступности и восстановлении. Если тариф позволяет задать задержку/повтор тревоги, требовать два последовательных неуспешных запроса до инцидента; при одиночной ошибке повторно проверить вручную. Интервал бесплатного плана и поведение при продолжительном инциденте описаны в [справке UptimeRobot](https://help.uptimerobot.com/en/articles/11360876-what-is-a-monitoring-interval-in-uptimerobot).

### Проверка после каждого деплоя

Workflow после GitHub Pages deployment делает до 11 запросов с интервалом 10 секунд, пока сайт не ответит успешно, и проверяет ожидаемый `<title>`. Если проверка не проходит, запуск Actions помечается ошибкой, поэтому проблему видно прямо в истории деплоев.

### Реакция на тревогу

1. Открыть страницу [GitHub Actions](https://github.com/leonidchekin55/tutor-marketplace-devops-demo/actions) и проверить последний запуск `Checks and deploy`, особенно шаг `Smoke check the deployed site`.
2. Если деплой прошёл, но внешний монитор сообщает о сбое, проверить, воспроизводится ли ошибка из другой сети, а затем посмотреть статус GitHub Pages/GitHub Status.
3. Уведомить второго контакта при подтверждённой недоступности. После восстановления проверить главную страницу и отметить время начала и окончания инцидента.

### Ошибки приложения

Сейчас сайт статический, поэтому клиентский Sentry не добавлен: JavaScript приложения для отслеживания ошибок нет. Если появится интерактивный код или API, подключить Sentry для frontend и backend, задать окружения `production`/`staging`, выпускать source maps только в Sentry, а в алертах сообщать о новых ошибках и всплеске частоты. Перед отправкой событий исключить email, имена детей и другие персональные данные. Для backend также добавить `/health` endpoint с проверкой зависимости от базы данных и отдельный HTTP-монитор.

Внешний монитор UptimeRobot пока описан как настройка и не подключён к аккаунту.

## Локальная проверка

```sh
pnpm install --frozen-lockfile
pnpm run lint
pnpm test
```
